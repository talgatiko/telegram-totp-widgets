# Аудит безопасности TOTP-бота и виджета

Дата: 2026-11-11. Отчёт рассматривает безопасность обработчика и виджета. Результаты проверок генератора приведены отдельно.

## Ответы владельца и решения

| Пункт | Ответ владельца | Решение для отчёта |
|---|---|---|
| SEC-02: исходное сообщение после ошибки | Пользователь может самостоятельно удалить ненужное сообщение; неполный ввод не считать проблемой. | Принято: исправление не требуется. Исходный текст остаётся техническим фактом, ручное удаление зависит от пользователя. |
| SEC-04: нагрузка на сервер | Скрипт работает на бесплатной серверной платформе Telegram, только формирует виджет и не хранит данные; перегрузка серверов — зона ответственности платформы. | Принято: ограничение частоты не входит в требуемые изменения. Расходы, квоты и пределы платформы не измерялись; бесплатность не подтверждает отсутствие лимитов или влияния на доступность бота. |
| SEC-07: буфер обмена | Риски копирования — ответственность пользователя. | Принято: предупреждение и иные изменения не требуются; копирование остаётся ручным. |
| SEC-05: генератор | Провести проверку виджета по независимому источнику. | Выполнена проверка по RFC 6238 и независимому HMAC в Node; результаты ниже. |

## Резюме и приоритеты

Главный риск — долговременный TOTP-секрет доступен в данных сообщения Telegram и проходит через обработчик бота. Это архитектурное решение ранее принято пользователем, а не обнаруженное нарушение ТЗ; оно несовместимо с моделью, в которой компрометация Telegram не раскрывает второй фактор. Наличие отдельного пароля основного сервиса само по себе не устраняет риск утечки второго фактора.

| Приоритет | ID | Уровень | Проблема и первый шаг |
|---|---|---|---|
| 1 | SEC-01 | Высокий, архитектурный риск | Доступ к содержимому чата даёт долговременный секрет: явно обозначить границу доверия и предусмотреть перевыпуск скомпрометированных ключей. |
| 2 | SEC-02 | Принят пользователем | Ошибочные и неоднозначные запросы с секретом остаются в чате; ненужные сообщения пользователь удаляет самостоятельно. |
| 3 | SEC-03 | Средний | Повтор входящего события может создать дубль: определить гарантию обработки и, если нужна идемпотентность, согласовать журнал без секретов. |
| 4 | SEC-04 | Принят пользователем | Прикладная квота отсутствует; ограничение платформы оставлено в зоне ответственности Telegram. |
| 5 | SEC-05 | Средний | Свои реализации криптографии и неполный актуальный полный прогон: завершить независимые проверки и клиентскую матрицу без настоящих ключей. |

Уровень описывает потенциальное последствие, а не факт атаки. Вероятности ниже — инженерные оценки без статистики инцидентов.

## Защитные свойства и ограничения

- Проверяются личный чат, совпадение отправителя с идентификатором чата и тип входного сообщения (`scripts/runtime-bot.js:59–61`). Это доверяет подлинности события от Telegram и не заменяет защиту Telegram-аккаунта.
- Название записывается через `textContent`, не через HTML (`tgcloud/lib/widget.js:163`); явного внедрения HTML через это поле при чтении не обнаружено. Отсутствие находки не является доказательством отсутствия всех инъекций.
- Base32, длина секрета и параметры URI ограничены (`tgcloud/lib/input.js:15–34`, `:46–70`). Секреты не обнаружены в формируемых штатных сообщениях об ошибках по просмотренным веткам; сохранность и настройки платформенных логов неизвестны.
- Ошибки расчёта скрывают старый код и отключают копирование (`tgcloud/lib/widget.js:185–193`). Попытка скопировать код предварительно обновляет расчёт (`:196–203`).
- Бот не отправляет повтор автоматически при неизвестном результате; это снижает риск дублей, но не решает повторную доставку входящего события.

## Проверка генератора

Источник независимых эталонных значений — [RFC 6238, приложение B](https://datatracker.ietf.org/doc/html/rfc6238#appendix-B), а не веб-сайт, которому передают реальные секреты. Запущен `node --test test/release-rfc6238.test.js`: собранный локальный обработчик и его общий виджет совпали со всеми 18 эталонными векторами (три алгоритма, шесть моментов времени, 8 цифр). При создании теста первая проверка SHA512 не прошла из-за ошибочно скопированного тестового ключа; после исправления ключа повтор прошёл. Это была ошибка тестовой фикстуры, не подтверждённая ошибка виджета.

Дополнительно `node --test test/widget.test.js test/minify-widget.test.js test/totp-check.test.js`: 28/28 тестов прошли, в том числе известные векторы, длины и сравнение с независимым Node `crypto`. Выполнен `node scripts/totp-check.mjs test --count 100 --seed audit-20261111 --mode shared --output reports/audit-oracle-100.json`: 100/100 комбинаций, 4900 проверок, SHA1, длины 10–17 байт, оба размера кода и семь периодов. Эти 100 случаев не охватывают всю матрицу; полный прогон 2310 комбинаций данной версии не подтверждён. Node VM с подменой Telegram API не доказывает исполнение QuickJS в клиенте. Реальные секреты никуда не передавались. `oathtool` найден как существующий генератор, но локально не установлен и в этих проверках не запускался.

## Обязательные вопросы

1. **Потеря данных:** удаление виджета или истории, утрата Telegram-аккаунта либо отсутствие отдельного резерва; отказ отправки может оставить только исходный запрос. Удаление исходного сообщения после подтверждённого создания не доказывает наличие резервной копии.
2. **Компрометация:** доступ к чат-данным/устройству раскрывает долговременный секрет; доступ к буферу обмена может раскрыть текущий код. Захват Telegram, вредоносное ПО и фишинг — сценарии угроз, не обнаруженные инциденты.
3. **Незаметные сбои:** `reply` подавляет ошибки, включая возможный отказ уведомления об удалении; неверные, но допустимые часы не обнаруживаются; повторное событие может создать дубль.
4. **Рост нагрузки:** вероятнее всего, первыми ограничат доступность квоты и обработка исходящих сообщений либо потребление клиента множеством активных карточек. Это гипотеза на основании архитектуры, не результат нагрузочного теста; фактическое первое узкое место неизвестно.
5. **Приоритеты:** с учётом решений пользователя SEC-02, SEC-04 и SEC-07 приняты без изменений; остальные пункты требуют отдельного решения. Архитектурный компромисс SEC-01 нельзя устранить настройкой сообщения без изменения модели хранения.
